# Define account-equity and exposure accounting — Nobitex inputs

**Checked:** 2026-10-25
**Scope:** Current official Nobitex API docs (`apidocs.nobitex.ir`), its OpenAPI specs, `nobitex.ir/pricing`, plus a few small unauthenticated `apiv2.nobitex.ir` reads. No credentials were read, no private endpoint was called, no order was placed. Complements [nobitex-spot-api-contract.md](nobitex-spot-api-contract.md) (orders, fees table, auth, market data) — not repeated here.

## Bottom line

There is **no real-time server-side equity/portfolio-value endpoint**. Equity must be computed client-side from `POST /users/wallets/list` (`balance`, `blockedBalance`, `activeBalance` per currency) times a public price per market. The only server-side aggregate is a **daily** PnL report whose `total_balance` is not documented as to unit or cutoff, and which can be disabled for a user (`FeatureUnavailable`). The docs never define what `blocked` means for a resting order, and there is **no API that returns the account's fee tier or maker/taker rate**. Only one trading-day statement exists (fee tiers recalculated daily between 03:00 and 04:00), and it names no timezone. [Wallet list](https://apidocs.nobitex.ir/user_data/%D9%84%DB%8C%D8%B3%D8%AA-%DA%A9%DB%8C%D9%81-%D9%BE%D9%88%D9%84-%D9%87%D8%A7%DB%8C-%DA%A9%D8%A7%D8%B1%D8%A8%D8%B1) · [Portfolio spec](https://apidocs.nobitex.ir/openapi/portfolio.yaml) · [Pricing](https://nobitex.ir/pricing/)

## Findings

### 1. Balance endpoints and fields

- **Primary: `POST /users/wallets/list`** (`READ`, 20 req/min, optional body `type` = `spot`|`margin`|`credit`|`debit`, default `spot`). Returns `wallets[]` with `id`, `currency`, `balance`, `blockedBalance`, `activeBalance`, `rialBalance` (integer), `rialBalanceSell` (integer). This is the only documented response with all three spot quantities. [Doc](https://apidocs.nobitex.ir/user_data/%D9%84%DB%8C%D8%B3%D8%AA-%DA%A9%DB%8C%D9%81-%D9%BE%D9%88%D9%84-%D9%87%D8%A7%DB%8C-%DA%A9%D8%A7%D8%B1%D8%A8%D8%B1) · [Spec](https://apidocs.nobitex.ir/openapi/user_data.yaml)
- **Alternative: `POST /v2/wallets`** (`READ`, 15 req/min, body `currencies=btc,eth,usdt,rls`, `type`). Returns `wallets` as an **object keyed by currency** with `id`, `balance`, `blocked` — no `activeBalance`, so this shape differs from the list endpoint. [Spec](https://apidocs.nobitex.ir/openapi/user_data.yaml)
- **Not enough alone: `POST /users/wallets/balance`** (60 req/2 min, body `currency`) returns a single string `balance` and **no blocked amount**. [Spec](https://apidocs.nobitex.ir/openapi/user_data.yaml)
- **Units.** The specs give no unit text for any wallet field. Verified by live public data that RLS-market prices are **rial**: `USDTIRT` last trade `2698650`, i.e. ≈ 269,865 toman per USDT. So the `rls` wallet `balance` is almost certainly rial too (inferred, not stated). `balance` for a coin is an amount of that coin. `rialBalance`/`rialBalanceSell` are bare integers with no documented unit or meaning (inferred: rial valuation of that wallet, and its sell-side variant). [Live stats](https://apiv2.nobitex.ir/market/stats?srcCurrency=usdt&dstCurrency=rls)
- **Equity endpoint: none.** Full user-data spec contains only profile, wallets, balances, transactions, deposits, withdrawals, cards/accounts and limitations — no total/portfolio value. The nearest thing is `POST /users/portfolio/last-week-daily-profit` returning `data[]` = `report_date`, `total_profit`, `total_profit_percentage`, `total_balance` (string), plus `monthly=true` for 30 days. It is **daily, not live**, returns `FeatureUnavailable` when the portfolio feature is off for the user, and its `total_balance` unit/valuation rule is undocumented. Treat it as a reconciliation cross-check at best, never as the bot's equity input. [Portfolio spec](https://apidocs.nobitex.ir/openapi/portfolio.yaml) · [Portfolio docs](https://apidocs.nobitex.ir/portfolio/%D8%B3%D9%88%D8%AF-%D9%88-%D8%B2%DB%8C%D8%A7%D9%86)

### 2. Blocked-balance semantics

- The docs expose blocked amounts (`blockedBalance`, `blocked`) and a separate available (`activeBalance`), but **contain no sentence describing what moves into `blocked`, or what happens on partial fill or cancel**. This is a documentation gap, not a documented rule. [Spec](https://apidocs.nobitex.ir/openapi/user_data.yaml)
- Two indirect signals support the usual reading (total = blocked + available): (a) the field names `balance` / `blockedBalance` / `activeBalance`; (b) `OverValueOrder` is defined as "order size or value exceeds the **available** balance" (`موجودی قابل استفاده`), which implies order admission is checked against available, i.e. funds already reserved by resting orders are excluded. **Inferred, not verified.** [Spot spec errors](https://apidocs.nobitex.ir/openapi/spot_trade.yaml)
- Cancel returns the order with `status: Canceled` and updated `unmatchedAmount`; the only related statement is that a canceled order may still have `matchedAmount > 0`. Nothing states when blocked funds are released back. [Cancel docs](https://apidocs.nobitex.ir/spot_trade/%D9%84%D8%BA%D9%88-%D8%B3%D9%81%D8%A7%D8%B1%D8%B4)
- **No WebSocket balance channel exists.** Documented channels are `orderbook`, `candle`, `trades`, `market-stats`, `private:orders`, `private:trades` only — so a balance change (fill, cancel, deposit) must be discovered by polling `/users/wallets/list` (20/min) or by reacting to private order/trade events and re-reading. [WebSocket spec](https://apidocs.nobitex.ir/openapi/websocket.yaml)

### 3. Prices for valuation

- **Current:** `GET /v3/orderbook/{symbol}` (symbol or `all`) → `bids`, `asks` as `[price, amount]` strings, `lastTradePrice`, `lastUpdate` (ms). Public, no token, 300 req/min. This is the newest and the one the changelog points at. [Spec](https://apidocs.nobitex.ir/openapi/market_data.yaml) · [Changelog](https://apidocs.nobitex.ir/changelog)
- **`GET /market/stats`** → per market: `isClosed`, `isClosedReason`, `bestBuy`, `bestSell`, `latest`, `mark`, `dayOpen`, `dayHigh`, `dayLow`, `dayClose`, `dayChange`, `volumeSrc`, `volumeDst`. Accepts `srcCurrency` and/or `dstCurrency` (comma lists); no args returns all markets; 20 req/min — the rate limit is the binding constraint if used per tick. `global.binance` is deprecated. [Spec](https://apidocs.nobitex.ir/openapi/market_data.yaml)
- **Also public:** `GET /v2/depth/{symbol}` (chart-shaped depth + `lastTradePrice`), `GET /v2/trades/{symbol}` (≤20 recent trades, `time` ms, `price`, `volume`, `type`), `GET /market/udf/history` (OHLC, ≤500 candles). [Spec](https://apidocs.nobitex.ir/openapi/market_data.yaml)
- **Not available / deprecated:** `GET /v1/ticker` → **HTTP 404**, and `GET /v1/orderbook/USDTIRT` → **HTTP 404**; neither exists in the current docs. `GET /v2/orderbook/USDTIRT` still answers `200` with the same shape, but the changelog records v2 order book as **deprecated** (v3 added, v2 deprecated, شهریور ۱۴۰۳). Use v3 only. [Live checks](https://apiv2.nobitex.ir/v2/orderbook/USDTIRT) · [Changelog](https://apidocs.nobitex.ir/changelog)
- **USDT/IRT exists.** Verified live: market key `usdt-rls` in `/market/stats`, symbol `USDTIRT` for orderbook/trades; `latest` 2,698,650. So USDT can be valued directly against rial with one market read. [Live stats](https://apiv2.nobitex.ir/market/stats?srcCurrency=usdt&dstCurrency=rls)
- **Symbol casing trap:** RLS-quoted markets are `*RLS` in order objects and `usdt-rls` in stats keys, but the **compact orderbook/WS symbol suffix is `IRT`** (`BTCIRT`, `USDTIRT`). `lastTradePrice`/`latest`/`bestBuy`/`bestSell` are decimal strings in the market's quote currency. The docs do not define `mark` vs `latest` for valuation, so pick one explicitly and record it. [Market-data spec](https://apidocs.nobitex.ir/openapi/market_data.yaml) · [WebSocket spec](https://apidocs.nobitex.ir/openapi/websocket.yaml)

### 4. Fees

- **Accrued fee is visible** in three places: order object `fee` (only when `details=2` on `GET /market/orders/list`, per the parameter description), trade list `fee` per trade, and the private trade WS event `fee`. [Order list](https://apidocs.nobitex.ir/spot_trade/%D9%81%D9%87%D8%B1%D8%B3%D8%AA-%D8%B3%D9%81%D8%A7%D8%B1%D8%B4-%D9%87%D8%A7%DB%8C-%DA%A9%D8%A7%D8%B1%D8%A8%D8%B1) · [Spec](https://apidocs.nobitex.ir/openapi/spot_trade.yaml)
- **Maker/taker per fill is only in the WS trade event** (`isMaker: boolean`). The REST trade list has no `isMaker`. [WebSocket spec](https://apidocs.nobitex.ir/openapi/websocket.yaml)
- **No fee-tier/rate endpoint.** `/v2/options` exposes `withdrawLimits`, `minOrders`, `amountPrecisions`, `pricePrecisions`, withdraw fees per network — **no spot fee rates and no user tier**. `/users/profile` returns an opaque `tradeStats` object with no documented fields. So the account's current tier and rate cannot be read from the API today. [Options spec](https://apidocs.nobitex.ir/openapi/options.yaml) · [User-data spec](https://apidocs.nobitex.ir/openapi/user_data.yaml)
- **Pre-fill rate is knowable only as a rule, not as data.** Pricing states tiers come from 30-day volume, differ for Toman vs Tether markets and maker vs taker, and charge the fee on the asset received. One extra operational detail: at order entry the UI shows the **taker** rate, but if the order rests and later fills as maker, the **maker** rate is deducted — so a resting limit order's final fee is not the pre-trade number shown. For reservations, assume the taker rate for that market type (conservative) or make it configurable. [Pricing](https://nobitex.ir/pricing/) · [Fee table in prior note](nobitex-spot-api-contract.md)

### 5. Trading-day semantics

- **The only "day" statement in the docs** is on the pricing page: tiers follow 30-day volume ending on the trade day, and "the 30-day volume calculations are performed and updated at the start of each day, **03:00–04:00 in the morning**" (`ابتدای هر روز، ساعت ۰۴:۰۰ - ۰۳:۰۰ بامداد`). **No timezone is named** on the page. Iran local time (Asia/Tehran, UTC+03:30, no DST since 2022) is the natural reading but is **inferred, not documented**. The wording is also ambiguous about whether the window is recomputed once inside that hour. [Pricing](https://nobitex.ir/pricing/)
- **Market-data "day" is a rolling 24 h, not a calendar day.** The WS spec calls `market-stats` "24-hour market stats" and defines `dayChange` as the percent change "in the past 24 hours"; `dayOpen`/`dayHigh`/`dayLow`/`dayClose` belong to that 24 h frame. Do not treat them as Tehran-midnight values. [WebSocket spec](https://apidocs.nobitex.ir/openapi/websocket.yaml)
- **No documented trading day for PnL or equity.** The portfolio report carries only `report_date` (`format: date`) with no cutoff, timezone, or valuation-price rule. No endpoint returns "today's volume" or "today's PnL". Trade list covers the last 180 days; `/users/transactions-history` takes `from`/`to` Unix seconds but the maximum allowed range is not published ("must not exceed the backend limit"). [Portfolio spec](https://apidocs.nobitex.ir/openapi/portfolio.yaml) · [User-data spec](https://apidocs.nobitex.ir/openapi/user_data.yaml)
- **Consequence:** if the bot needs a daily window, define it in the bot (document the choice) and do not claim Nobitex parity; the only vendor boundary you can rely on is the 03:00–04:00 fee-tier refresh.

### 6. Precision and rounding

- General notes tell clients to send monetary values as **strings** because `float` is not suitable for precise financial use. Wallet values are decimal **strings** (`balance`, `blockedBalance`, `activeBalance`, `blocked`), but `rialBalance`/`rialBalanceSell` are bare JSON **integers** — so the payload mixes both types. [General notes](https://apidocs.nobitex.ir/general_notes) · [Spec](https://apidocs.nobitex.ir/openapi/user_data.yaml)
- `/v2/options` gives `amountPrecisions` and `pricePrecisions` per market (tick steps for **orders**) and `displayPrecision` per coin, plus `minOrders` per quote currency. None of these define how many decimals a wallet balance has, and none is an equity-rounding rule. [Options spec](https://apidocs.nobitex.ir/openapi/options.yaml)
- Practical rule (engineering, not vendor-documented): parse all amounts into exact decimals, multiply by exact decimal prices, and round only the final rial figure — never the per-wallet terms. The docs state no rounding mode for valuation anywhere.

## Unresolved

1. **What `blockedBalance` / `activeBalance` / `blocked` actually mean**, whether a resting limit buy blocks quote, a resting sell blocks base, and exactly when blocked amounts are released on partial fill or cancel. No doc text; needs an authenticated testnet experiment (out of scope here).
2. **Unit of the `rls` wallet `balance`** (rial vs toman) and of `rialBalance` / `rialBalanceSell`. Rial is inferred from rial-denominated market prices, not stated.
3. **Unit, timestamp and valuation rule of `total_balance`** in `/users/portfolio/last-week-daily-profit`, and whether that feature is enabled for the account.
4. **Fee tier / maker-taker rate**: no API exposes it; the actual account tier cannot be determined from public docs, and the maker rate that will apply to a resting order is unknown before the fill.
5. **Timezone of the 03:00–04:00 daily volume recalculation**, and whether `report_date` uses the same boundary.
6. **Exact decimal places of wallet balances**, and the maximum range accepted by `/users/transactions-history`.
7. **Whether `mark` or `latest`/`lastTradePrice` is the intended valuation price** — the docs define neither field's role.
8. Whether `/v2/orderbook/*` (still returning 200) is guaranteed to stay available; it is marked deprecated.
